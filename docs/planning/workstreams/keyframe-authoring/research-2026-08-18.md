# PL20 three-track review: cheaper keyframe authoring with the register in weights

**Status: research complete 2026-08-18. Nothing built, nothing dispatched, $0 spent.**
Plan of record: [`design.md`](design.md). Predecessor, closed: **PL17**,
[`findings/image-edit-model-alternatives.md`](../../../findings/image-edit-model-alternatives.md).
Baseline, frozen and untouched: **banana interpolation v1**.

You are picking up the answer to "what is cheaper than nano banana with more creative
control". Read section 1 first; it corrects two premises in the kickoff brief that would
otherwise send you down a longer road than necessary.

---

## 0. The one-paragraph answer

There is a **2x saving available this week for the cost of one CLI flag**
(`gemini-3.1-flash-lite-image`, $0.0336 against $0.067, same API, same code path, same
provider), and an **11x to 35x saving available for the cost of one LoRA** (FLUX.2 klein
4B on Modal, ~$0.02 to $0.06 per chain). The second is also the answer to Track 1, because
klein runs generation and editing through **one pipeline**, so a single style LoRA puts the
painterly register in weights for *both* jobs. And the edit-LoRA training set **already
exists on disk**: 113 instruction-labelled before/after pairs across 20 chains, in exactly
the (condition, target, instruction) triplet format that first-party diffusers now trains
on. The open risk is unchanged from PL17 and is not economic: klein's preservation failure
was architectural, and nobody has shown a LoRA repairs it.

---

## 1. Two premises in the brief that are wrong, both checked against the repo

Fix these before planning anything, because each one changes what you have to test.

### 1.1 "Honour exact non-square dimensions" is NOT a live requirement

The brief lists exact 1408x768 and 1024x1280 as a Track 1 requirement, and PL17 section
10.3 spent real effort establishing that every candidate needs explicit `height`/`width`.

**The incumbent does not meet it and never has.** Every `manifest.json` on disk records the
raw banana output size, and not one is a target size:

| chain | recorded size | target |
|---|---|---|
| `action_mist`, `action_shore`, `work_bricks`, `work_kiln` | **1376x768** | 1408x768 |
| `labor_bedroom`, `labor_vert_steps`, `work_bell` | **928x1152** | 1024x1280 |

[`tools/loop_render.py:73`](../../../../tools/loop_render.py#L73) LANCZOS-resizes every
keyframe to `--width`/`--height` before interpolation. The resize is already absorbed.

**Consequence:** a candidate only has to land the right *aspect*, not the right *pixels*.
That widens the field, retires a test, and specifically de-risks
`gemini-3.1-flash-lite-image`, whose 14 fixed aspect ratios were the obvious objection to it.

### 1.2 Track 1's measured failure has a zero-cost fix that is not a model

"Three verticals rendered photographic because the style clause was dropped" is a
**prompt-plumbing bug, not a model deficiency.** `banana_keyframes.py` already carries
`BASE_SUFFIX`, appended to every base prompt precisely so a clause cannot be forgotten, and
it currently suppresses only signatures, lettering and canvas edges. The painterly register
clause is not in it.

**Put the register clause in `BASE_SUFFIX` and the measured failure cannot recur**, on the
incumbent, today, for nothing. Do this regardless of which track wins. It does not put the
register in weights and it does not make the case for a LoRA go away, but it stops the
specific bleeding while the LoRA work runs.

## 2. TRACK 1 recommendation: generation with the register in weights

**Train a style-only LoRA on FLUX.2 [klein] 4B. Keep SDXL + Hammershoi for
structure-critical pieces only.**

### Why klein and not a fourth backbone

| candidate | licence | verdict |
|---|---|---|
| **FLUX.2 [klein] 4B** (`black-forest-labs/FLUX.2-klein-base-4B`) | **Apache 2.0** | **Recommended.** One unified pipeline for t2i AND edit, so one LoRA serves both tracks. First-party LoRA training (`train_dreambooth_lora_flux2_klein.py`), BFL training docs, ostris support. 4B, ~13 GB. Already staged on `slow-interp-edit-cache` and already wired into `cloud/edit.py`. |
| SDXL + `Hammershoi_Interiors_epoch_10` | fine | **Keep, do not retire.** The only route with a proven ControlNet lever in this repo (`skills/control-map`, `tools/make_massing.py`, the drawn massing map that beat three derived maps). Klein ControlNet exists but is community-grade. |
| Z-Image / Z-Image-Turbo (6B, Apache 2.0) | fine | **No.** Good generator, but **Z-Image-Edit still does not exist** (re-verified 2026-08-18, `Tongyi-MAI/Z-Image` issue #169). Choosing it forfeits the unified-pipeline argument, which is the whole reason klein wins. |
| Qwen-Image 2.0 (Apache 2.0) | fine | **No.** No unified edit path we can fine-tune; see section 3. |

### Is one LoRA enough

**Yes, and it should be style-only, not interiors-specific.** BFL guidance for a style LoRA
is 15 to 40 single images with content-only captions, 1500 to 3000 steps, rank 128/64/64/32.
The series spans interiors, landscapes, shores and brickyards, so an interiors-conditioned
artefact is the wrong shape. Train on gated keeper frames drawn across all four clusters and
let the subject come from the prompt.

**Recommended new artefact:** an `arendt_register` style LoRA on klein 4B. It replaces the
forgettable clause, and it is available at edit time for free because klein is one pipeline.

### Prompt control and dimensions

Klein takes explicit `height`/`width` (PL17 measured exact 1408x768, 592x1792, 1856x576) and
the fal schema confirms arbitrary width and height up to 14,142 px. Per section 1.1 this is
now a convenience, not a gate.

## 3. TRACK 2 recommendation: editing at a fraction of $0.067

**Two tiers, run in this order.**

### Tier 1, this week: flip the model flag

`gemini-3.1-flash-lite-image` (Nano Banana 2 Lite) is **$0.0336 per 1K image against
$0.067**, GA, same `generate_content` call, same `response_modalities`, documented for image
editing and multi-image composition. `banana_keyframes.py` already exposes `--model`, so
**the change is a flag, not a patch**.

It is not the answer to the brief. It buys exactly 2x and buys nothing on creative control
or fragility, since it is the same meter that depleted mid-production. It is worth doing
because it is nearly free to try and halves the bill if the register holds.

Also live, and worth knowing: the **Gemini Batch API is 50% off and applies to image output**
($0.034 for full-fat banana, $0.0168 for lite). It is **useless for a chain**, because every
edit consumes the previous output, so a 9-edit chain cannot be batched. It is usable only for
independent base frames across many chains.

### Tier 2, the real prize: klein 4B carrying an edit LoRA distilled from our own chains

This is the test PL17 section 10.9 named and never ran, and the training data is already ours.

`train_dreambooth_lora_flux2_img2img.py` shipped in first-party diffusers and trains on
**(condition image, target image, instruction text) triplets**. That is precisely the shape of
a banana chain: frame N, frame N+1, and the `--edit` string recorded in `manifest.json`.

**Measured on disk today: 113 labelled pairs across 20 chains with manifests** (`ledA_window_v2`
and `_v3` at 9 each, `ledB_snow_v3` at 8, down to 4). BFL guidance for an edit LoRA is 50 to 200
pairs, and their worked example used 120. **We are inside the recommended range without
generating a single new image.**

What this trains is not a style. It trains the *inversion itself*, "output equals input except
X", in our register, from the model that already does it correctly. It is distillation of nano
banana's edit behaviour into a 4B model we own.

Use the **first-party diffusers trainer, not ostris/ai-toolkit**, and load with the same
`Flux2KleinPipeline` that `cloud/edit.py` already instantiates. ai-toolkit-trained klein 4B
LoRAs currently fail to load in diffusers with a `KeyError` in
`_convert_non_diffusers_flux2_lora_to_diffusers()`; the issue is open on **both** repos
(`black-forest-labs/flux2` #33, `ostris/ai-toolkit` #667), filed 2026-01-23, still open on
2026-08-18, no stated workaround. Training and inference through one library sidesteps it.

### Rejected, with reasons

| candidate | why not |
|---|---|
| **Qwen-Image-Edit-2511** | PL17 held it in reserve as "the one model we could realistically fine-tune". That is **no longer its advantage**: LoRA fine-tuning is not officially supported, community implementations only, while klein has three first-party training scripts. Documented pixel drift still attacks our instruments. **Klein has taken its seat.** |
| Hosted budget editors, $0.003 to $0.015 per image | Mostly FLUX.1 Kontext [dev] resold, which is the **non-commercial licence trap** of PL17 section 4, or unverifiable provenance. Re-buys the fragility that bit us twice and cannot win clearly enough to justify it. |
| nano banana via fal, $0.08 | More expensive than going direct to Google. |
| FireRed, Mage-Flow | Closed by PL17. Do not re-probe. |

### Multi-image, now that the requirement is softer

Both live routes keep it anyway: `gemini-3.1-flash-lite-image` does multi-image composition,
and fal's klein edit endpoints take **up to 4 input images**. No candidate was admitted or
excluded on this axis, which is the right outcome given that seven authored intermediates
failed on a colour-temperature gap.

### Break-even

A $6 LoRA pays for itself against banana in **about 10 chains, one production day**, at Modal
rates. Against flash-lite it takes about 19 chains, two days. **Unlike PL17, the saving does
not evaporate on inspection.** State that plainly, then state the next line just as plainly.

### Say the absolute figure out loud

**$4 to $6 a day is modest and nobody should migrate for it.** The three arguments that hold:

1. **Creative control.** The register is a forgettable prompt clause today and it has already
   been forgotten three times. Weights cannot be forgotten. Section 1.2 patches the symptom;
   a LoRA removes the mechanism.
2. **Cost per experiment.** A retry costs $0.067 today and about $0.0015 warm on Modal. That
   is 45x, and it changes behaviour rather than the invoice: you stop rationing retries, dead
   chains and collapsed bridges.
3. **Fragility.** The meter depleted mid-production once, then failed again as an invalid key
   that read exactly like depletion. `review_gate.py` runs on the same meter, so keyframes and
   the gate die together. Moving keyframes off it halves that blast radius.

## 5. TRACK 3 recommendation: the pipeline worth testing, kill gate first

Name it **`klein interpolation v1`**. Never merge into `edit-model-loop`; banana interpolation
v1 stays frozen and is the thing being measured against.

### The named first probe: P1, the flag flip

**`--model gemini-3.1-flash-lite-image`, re-running an existing chain's own manifest.**

- Target **`action_mist`**, not `labor_embers`. `labor_embers` predates the manifest flag and
  has **no `manifest.json`**, so its prompts are unrecoverable and a re-run would not be a
  single-variable swap. `action_mist` is the **10/10/10/9** piece, the best the baseline has
  produced, and its manifest is complete: base prompt, `BASE_SUFFIX` on, 4 edits, 5 frames at
  1376x768.
- **Cost: 5 images at $0.0336 = about $0.17.** No Modal dispatch, no GPU, no new pipeline code.
- Instrument: the PL17 section 10.2 crop test re-anchored to this subject. The edits veil depth
  (far ridge, farmhouse, poplars), so the **foreground drystone wall and well head are
  legitimately untouched**. Use box `0,384` to `704,768`, which is 704x384, the same crop size
  PL17 used, over dense masonry where edge-crispening shows first. Pair it with
  `tools/chain_stats.py` and the chroma delta.
- **The banana reference numbers cost nothing.** PL17's 0.870 / 1.21 / +7.4 were measured on a
  different subject and do not transfer. Compute this chain's own reference from `0000.png` and
  `0001.png`, already on disk, then measure lite against it. Same subject, same crop, same edit
  string, one variable.
- **You will have to write the measurement.** The PL17 Q1 instrument did not survive as a tool:
  nothing under `tools/` takes two images and a crop box and returns SSIM, Laplacian-variance
  ratio and warmth. `analyse_ladder.py` has a fixed crop but builds contact sheets. Budget about
  40 lines, and put it in `tools/` rather than the scratchpad this time, because P2 needs the
  identical instrument to compare against klein's bare 0.487.
- **Go if** untouched-region SSIM >= 0.80, lapvar <= about 1.3, and the register holds by eye at
  native resolution. **No-go** if lite's distillation costs the soft blending, which is the first
  thing distillation costs.

P1 is chosen because it is the only probe that can be run and judged **before any LoRA exists**,
it reuses instruments that already carry reference numbers, and a pass halves the bill
immediately. **It is not the answer to the brief.** Do not let a P1 pass end the workstream.

### P2, which is the actual Phase 1 kill gate

Design.md Phase 1 asks whether the chosen route can author a controlled delta at all. For klein
that cannot be asked until the LoRA exists, so P2 is:

1. Build the triplet set from the 113 pairs. **Filter to gated keepers first**; `labor_vert_steps`
   walked its geometry twice and its pairs teach the failure. Expect to keep well under 113.
2. Train the edit LoRA with `train_dreambooth_lora_flux2_img2img.py` on Modal L40S. **$4 to $6.**
3. Add `load_lora_weights` to `KleinEditor` in `cloud/edit.py`. One class, one line; the rig is
   already validated.
4. Re-run the Q1 crop test on `labor_embers/keyframes/0000.png` at PL17's original box `100,384` to
   `804,768`, seed 1087, so the number lands in the same column as klein's bare **0.487**. This one
   stays on `labor_embers` because that is the base PL17 measured klein against; the missing manifest
   does not matter here, since P2 supplies its own single edit instruction rather than replaying a chain.
5. **Go if** untouched-region SSIM >= 0.80 and consecutive structure r >= 0.9 with the named element
   visibly changed. **No-go, and the route closes**, if klein still repaints the frame.

Then, each stopping on a no-go: the five-edit run for the geometry walk, the full 300-frame loop
through the unchanged `tools/loop_render.py`, `tools/review_gate.py` against the keeper floor with
mandatory eye signoff, and a head-to-head against banana interpolation v1 on the same subject,
published side by side on the field so Luca judges them together.

**Budget to reach the P2 verdict: about $7.** Route every dispatch through the `modal` subagent
and say so before spending.

## 6. What is still unknown, stated honestly

**The one that decides it:**

1. **Whether a LoRA repairs klein's preservation.** It is the premise of this whole workstream and
   it is not established. Klein bare scored **0.487** untouched-region SSIM against nano banana's
   0.870, with warmth **+38.3** against +7.4. A style LoRA changes what klein paints *in*; it is a
   much weaker claim that it stops klein *repainting*. And part of the cause is architectural, not
   stylistic: `Flux2KleinPipeline` calls `_resize_to_target_area(img, 1024*1024)` on any reference
   above 1 MP, so every edit takes a downsample-then-upsample round trip that no LoRA touches. The
   **edit** LoRA is the mechanism with a real chance, because before/after pairs train the
   identity-except-X behaviour directly. Nobody has shown it recovers 0.487 to 0.90.
   **Treat a clean negative here as the expected outcome and a first-class result.**

**The rest, roughly in order of how much they cost to discover late:**

2. Whether flash-lite holds the painterly register. Distillation costs soft blending first, and soft
   blending is the aesthetic. P1 settles it for $0.17.
3. Whether the filtered keeper pair count clears BFL's 50-pair floor. 113 exist; the gated subset is
   unmeasured.
4. **LoRA format interop.** The ostris and diffusers `KeyError` is open and seven months old. The
   first-party-trainer route should sidestep it and is unverified. fal's `loras[].path` accepts a URL
   or an HF repo id but the expected format is undocumented, so the fal fallback may need a different
   export than Modal does.
5. **`cloud/edit.py:200` names `black-forest-labs/FLUX.2-klein-4B`. The live repo is
   `black-forest-labs/FLUX.2-klein-base-4B`.** It resolved on 2026-08-14, so it is probably a
   redirect, but PL17 lost a container start to exactly this class of error. Check on contact.
6. Whether a LoRA'd klein can do the dual-endpoint bridge. Klein's bridge was never tested; it died
   at Q1. FireRed's composited rather than interpolated. The requirement is softer now, but it is
   untested, not solved.
7. Whether klein ControlNet is usable here. It exists (Diffusion Templates trained on
   klein-base-4B, Civitai depth workflows) but is community-grade against SDXL's first-party
   ecosystem. **Do not retire the SDXL structural route on this evidence.**
8. Whether flash-lite's 14 fixed aspect ratios cover 1408x768 (11:6, not in the list) closely enough.
   Per section 1.1 the resize is already absorbed, so this is likely cosmetic. Likely, not verified.
9. Whether the Modal warm-container economics survive real production. $0.019 per chain assumes one
   container across nine chains; a cold start per chain triples it to $0.057, which is still 11x.
