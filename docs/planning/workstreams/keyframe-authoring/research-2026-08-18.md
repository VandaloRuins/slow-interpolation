## 0. The one-paragraph answer

There is a **1.8x saving available today for the cost of one CLI flag, and it is now measured,
not projected** (section 8): `gemini-3.1-flash-lite-image` fails the painterly gate as a
generator but **beats nano banana on every instrument as an editor**, and edits are 9 of the
10 calls in a chain. Route the edits to lite, keep the base on banana, and a chain drops from
$0.670 to $0.369 with no new model, no GPU and no register risk.

That leaves job A, the base frame, as the one unsolved job, which is the right target for a
**style LoRA on FLUX.2 [klein] 4B** (Apache 2.0, one unified pipeline for generation and
editing, first-party LoRA training, already staged on `slow-interp-edit-cache` and already
wired into `cloud/edit.py`). Self-hosting the edits on klein would take a chain to **$0.02 to
$0.06**, an 11x to 35x saving, but that prize shrank when lite solved job B for free, so the
LoRA case now rests on **creative control rather than cost**. The edit-LoRA training set still
exists on disk if wanted: 113 instruction-labelled before/after pairs across 20 chains, in the
exact (condition, target, instruction) triplet format first-party diffusers trains on. The open
risk is unchanged from PL17 and is not economic: klein's preservation failure was architectural,
and nobody has shown a LoRA repairs it.

## 1. Two premises in the brief that are wrong, both checked against the repo

Fix these before planning anything, because each one changes what you have to test.

### 1.1 "Honour exact non-square dimensions" is NOT a live requirement

The brief lists exact 1408x768 and 1024x1280 as a Track 1 requirement, and PL17 section
10.3 spent real effort establishing that every candidate needs explicit `height`/`width`.

**The incumbent does not meet it and never has.** Every `manifest.json` on disk records the
raw banana output size, and not one is a target size:

| chain | recorded size | target |
|---|---|---|
| `action_mist`, `action_shore`, `work_bricks`, `work_kiln` | **1376x768** | 1408x768 |
| `labor_bedroom`, `labor_vert_steps`, `work_bell` | **928x1152** | 1024x1280 |

[`tools/loop_render.py:73`](../../../../tools/loop_render.py#L73) LANCZOS-resizes every
keyframe to `--width`/`--height` before interpolation. The resize is already absorbed.

**Consequence:** a candidate only has to land the right *aspect*, not the right *pixels*.
That widens the field, retires a test, and specifically de-risks
`gemini-3.1-flash-lite-image`, whose 14 fixed aspect ratios were the obvious objection to it.

### 1.2 Track 1's measured failure has a zero-cost fix that is not a model

"Three verticals rendered photographic because the style clause was dropped" is a
**prompt-plumbing bug, not a model deficiency.** `banana_keyframes.py` already carries
`BASE_SUFFIX`, appended to every base prompt precisely so a clause cannot be forgotten, and
it currently suppresses only signatures, lettering and canvas edges. The painterly register
clause is not in it.

**Put the register clause in `BASE_SUFFIX` and the measured failure cannot recur**, on the
incumbent, today, for nothing. Do this regardless of which track wins. It does not put the
register in weights and it does not make the case for a LoRA go away, but it stops the
specific bleeding while the LoRA work runs.

## 2. TRACK 1 recommendation: generation with the register in weights

**Train a style-only LoRA on FLUX.2 [klein] 4B. Keep SDXL + Hammershoi for
structure-critical pieces only.**

### Why klein and not a fourth backbone

| candidate | licence | verdict |
|---|---|---|
| **FLUX.2 [klein] 4B** (`black-forest-labs/FLUX.2-klein-base-4B`) | **Apache 2.0** | **Recommended.** One unified pipeline for t2i AND edit, so one LoRA serves both tracks. First-party LoRA training (`train_dreambooth_lora_flux2_klein.py`), BFL training docs, ostris support. 4B, ~13 GB. Already staged on `slow-interp-edit-cache` and already wired into `cloud/edit.py`. |
| SDXL + `Hammershoi_Interiors_epoch_10` | fine | **Keep, do not retire.** The only route with a proven ControlNet lever in this repo (`skills/control-map`, `tools/make_massing.py`, the drawn massing map that beat three derived maps). Klein ControlNet exists but is community-grade. |
| Z-Image / Z-Image-Turbo (6B, Apache 2.0) | fine | **No.** Good generator, but **Z-Image-Edit still does not exist** (re-verified 2026-08-18, `Tongyi-MAI/Z-Image` issue #169). Choosing it forfeits the unified-pipeline argument, which is the whole reason klein wins. |
| Qwen-Image 2.0 (Apache 2.0) | fine | **No.** No unified edit path we can fine-tune; see section 3. |

### Is one LoRA enough

**Yes, and it should be style-only, not interiors-specific.** BFL guidance for a style LoRA
is 15 to 40 single images with content-only captions, 1500 to 3000 steps, rank 128/64/64/32.
The series spans interiors, landscapes, shores and brickyards, so an interiors-conditioned
artefact is the wrong shape. Train on gated keeper frames drawn across all four clusters and
let the subject come from the prompt.

**Recommended new artefact:** an `arendt_register` style LoRA on klein 4B. It replaces the
forgettable clause, and it is available at edit time for free because klein is one pipeline.

### Prompt control and dimensions

Klein takes explicit `height`/`width` (PL17 measured exact 1408x768, 592x1792, 1856x576) and
the fal schema confirms arbitrary width and height up to 14,142 px. Per section 1.1 this is
now a convenience, not a gate.

## 3. TRACK 2 recommendation: editing at a fraction of $0.067

**Two tiers, run in this order.**

### Tier 1, this week: flip the model flag

`gemini-3.1-flash-lite-image` (Nano Banana 2 Lite) is **$0.0336 per 1K image against
$0.067**, GA, same `generate_content` call, same `response_modalities`, documented for image
editing and multi-image composition. `banana_keyframes.py` already exposes `--model`, so
**the change is a flag, not a patch**.

It is not the answer to the brief. It buys exactly 2x and buys nothing on creative control
or fragility, since it is the same meter that depleted mid-production. It is worth doing
because it is nearly free to try and halves the bill if the register holds.

Also live, and worth knowing: the **Gemini Batch API is 50% off and applies to image output**
($0.034 for full-fat banana, $0.0168 for lite). It is **useless for a chain**, because every
edit consumes the previous output, so a 9-edit chain cannot be batched. It is usable only for
independent base frames across many chains.

### Tier 2, the real prize: klein 4B carrying an edit LoRA distilled from our own chains

This is the test PL17 section 10.9 named and never ran, and the training data is already ours.

`train_dreambooth_lora_flux2_img2img.py` shipped in first-party diffusers and trains on
**(condition image, target image, instruction text) triplets**. That is precisely the shape of
a banana chain: frame N, frame N+1, and the `--edit` string recorded in `manifest.json`.

**Measured on disk today: 113 labelled pairs across 20 chains with manifests** (`ledA_window_v2`
and `_v3` at 9 each, `ledB_snow_v3` at 8, down to 4). BFL guidance for an edit LoRA is 50 to 200
pairs, and their worked example used 120. **We are inside the recommended range without
generating a single new image.**

What this trains is not a style. It trains the *inversion itself*, "output equals input except
X", in our register, from the model that already does it correctly. It is distillation of nano
banana's edit behaviour into a 4B model we own.

Use the **first-party diffusers trainer, not ostris/ai-toolkit**, and load with the same
`Flux2KleinPipeline` that `cloud/edit.py` already instantiates. ai-toolkit-trained klein 4B
LoRAs currently fail to load in diffusers with a `KeyError` in
`_convert_non_diffusers_flux2_lora_to_diffusers()`; the issue is open on **both** repos
(`black-forest-labs/flux2` #33, `ostris/ai-toolkit` #667), filed 2026-01-23, still open on
2026-08-18, no stated workaround. Training and inference through one library sidesteps it.

### Rejected, with reasons

| candidate | why not |
|---|---|
| **Qwen-Image-Edit-2511** | PL17 held it in reserve as "the one model we could realistically fine-tune". That is **no longer its advantage**: LoRA fine-tuning is not officially supported, community implementations only, while klein has three first-party training scripts. Documented pixel drift still attacks our instruments. **Klein has taken its seat.** |
| Hosted budget editors, $0.003 to $0.015 per image | Mostly FLUX.1 Kontext [dev] resold, which is the **non-commercial licence trap** of PL17 section 4, or unverifiable provenance. Re-buys the fragility that bit us twice and cannot win clearly enough to justify it. |
| nano banana via fal, $0.08 | More expensive than going direct to Google. |
| FireRed, Mage-Flow | Closed by PL17. Do not re-probe. |

### Multi-image, now that the requirement is softer

Both live routes keep it anyway: `gemini-3.1-flash-lite-image` does multi-image composition,
and fal's klein edit endpoints take **up to 4 input images**. No candidate was admitted or
excluded on this axis, which is the right outcome given that seven authored intermediates
failed on a colour-temperature gap.

## 6. What is still unknown, stated honestly

**The one that decides it:**

1. **Whether a LoRA repairs klein's preservation.** It is the premise of this whole workstream and
   it is not established. Klein bare scored **0.487** untouched-region SSIM against nano banana's
   0.870, with warmth **+38.3** against +7.4. A style LoRA changes what klein paints *in*; it is a
   much weaker claim that it stops klein *repainting*. And part of the cause is architectural, not
   stylistic: `Flux2KleinPipeline` calls `_resize_to_target_area(img, 1024*1024)` on any reference
   above 1 MP, so every edit takes a downsample-then-upsample round trip that no LoRA touches. The
   **edit** LoRA is the mechanism with a real chance, because before/after pairs train the
   identity-except-X behaviour directly. Nobody has shown it recovers 0.487 to 0.90.
   **Treat a clean negative here as the expected outcome and a first-class result.**

**The rest, roughly in order of how much they cost to discover late:**

2. Whether flash-lite holds the painterly register. Distillation costs soft blending first, and soft
   blending is the aesthetic. P1 settles it for $0.17.
3. Whether the filtered keeper pair count clears BFL's 50-pair floor. 113 exist; the gated subset is
   unmeasured.
4. **LoRA format interop.** The ostris and diffusers `KeyError` is open and seven months old. The
   first-party-trainer route should sidestep it and is unverified. fal's `loras[].path` accepts a URL
   or an HF repo id but the expected format is undocumented, so the fal fallback may need a different
   export than Modal does.
5. **`cloud/edit.py:200` names `black-forest-labs/FLUX.2-klein-4B`. The live repo is
   `black-forest-labs/FLUX.2-klein-base-4B`.** It resolved on 2026-08-14, so it is probably a
   redirect, but PL17 lost a container start to exactly this class of error. Check on contact.
6. Whether a LoRA'd klein can do the dual-endpoint bridge. Klein's bridge was never tested; it died
   at Q1. FireRed's composited rather than interpolated. The requirement is softer now, but it is
   untested, not solved.
7. Whether klein ControlNet is usable here. It exists (Diffusion Templates trained on
   klein-base-4B, Civitai depth workflows) but is community-grade against SDXL's first-party
   ecosystem. **Do not retire the SDXL structural route on this evidence.**
8. Whether flash-lite's 14 fixed aspect ratios cover 1408x768 (11:6, not in the list) closely enough.
   Per section 1.1 the resize is already absorbed, so this is likely cosmetic. Likely, not verified.
9. Whether the Modal warm-container economics survive real production. $0.019 per chain assumes one
   container across nine chains; a cold start per chain triples it to $0.057, which is still 11x.

## 8. P1 results (2026-08-18)

**Verdict: the A/B decomposition in the kickoff brief is now MEASURED, not hypothesised.
`gemini-3.1-flash-lite-image` FAILS job A and PASSES job B.** Total spend $0.30, nine images.

Run on `action_mist` (the 10/10/10/9 piece), replaying its own manifest so only the model
differs. Instrument: `tools/crop_stats.py`, 704x384 untouched foreground at box `0,384` to
`704,768`, the drystone wall and well head, which the mist edits never name.

**Sizes: lite returned 1376x768, identical to full banana, on all nine images.** The
aspect-ratio worry in section 6 item 8 is closed. No snapping, no new resize.

### 8.1 The three ladders

Consecutive pairs in the untouched region. Higher ssim better, lapvar near 1.0 better,
warmth and chroma near 0 better.

| pair | banana ssim / lapvar | **lite, own base** | **lite, banana base** |
|---|---|---|---|
| 0->1 | 0.973 / 1.03 | 0.927 / 0.89 | **0.944 / 0.99** |
| 1->2 | 0.935 / 0.98 | 0.911 / 0.96 | **0.968 / 1.03** |
| 2->3 | 0.870 / 0.79 | 0.954 / 1.10 | **0.920 / 1.02** |
| 3->4 | 0.929 / 0.95 | 0.957 / 0.99 | **0.965 / 1.02** |
| **mean ssim** | **0.927** | **0.937** | **0.949** |
| **drift vs frame 0** | 0.790 / 0.76 | n/a, different base | **0.818 / 1.06** |
| chroma range | 1.0 to 3.2 | 1.8 to 2.8 | **1.2 to 2.3** |
| warmth range | -4.9 to +0.6 | -5.2 to -0.4 | **-3.3 to +0.7** |

**Lite beats banana on every quantitative axis, including the drift-against-frame-0 test that
PL17 section 10.6 established as the one that matters** (0.818 against 0.790). No yellow cast,
no crispening, no chroma excursion anywhere near the 11 threshold.

### 8.2 Job A, generation: FAIL on the hard-stop gate

Lite's own frame 0 holds the composition faithfully (drystone wall, well head, farmhouse,
poplars, ridge) and **fails the painterly register outright**, exactly the way three verticals
failed on the incumbent:

- Every stone individually delineated with hard edges and high local contrast, against
  banana's soft tonal masses with blurred boundaries.
- Palette swings from muted grey-green to **warm ochre and tan**.
- A **specular highlight on a galvanised bucket**, crisp mown grass stripes, sharply outlined
  poplars. It reads as detailed illustration, not soft tonal oil with sfumato.
- **A faint cursive signature in the bottom-left corner**, despite `BASE_SUFFIX` explicitly
  forbidding "NO signature, NO artist's name, NO monogram". Banana slips on this 1 in 6; lite
  slipped on its only base.

This is a **hard stop** (PL17 section 10.2). Do not author bases on lite.

### 8.3 Job B, editing: PASS, decisively

Handed banana's frame 0 via `--base-image` and given the identical four edits, lite produced
the best ladder of the three and **holds the register by eye at native resolution**. The 1:1
well-head crop of the final state is indistinguishable from banana's own final state: soft
grey tonal stone, blurred edges, muted palette, ground dissolving into mist.

**Confound ruled out:** an editor that changes nothing also scores perfectly on preservation.
It did not. The mist at state 4 fully performs the named change, the far ridge dissolved, the
farmhouse a faint shape, the poplars veiled, matching the "seventy-five percent of the depth"
instruction.

One real difference: **banana softens over a chain** (lapvar 0.76 against frame 0) while lite
holds surface energy flat (1.06). 1.06 is neutral, not crispening, and compounds to about 1.14
over nine edits. Banana's softening is its own kind of drift, so this is a difference, not a defect.

### 8.4 What this changes

**A chain is 1 base and 9 edits, so the edits are 90% of the calls.** Route them to lite and
keep the base on full banana and the chain goes **$0.670 to $0.369, a 1.8x saving available
today with no new model, no GPU, and no risk to the register.**

| route | base | 9 edits | chain | vs banana |
|---|---|---|---|---|
| banana throughout | $0.067 | $0.603 | $0.670 | 1x |
| **banana base + lite edits** | $0.067 | **$0.302** | **$0.369** | **1.8x** |
| lite throughout | $0.034 | $0.302 | $0.336 | 2.0x but **register fails** |

It also **sharpens the case for the klein LoRA rather than weakening it.** Track 2 is now
substantially solved for free, so the LoRA is no longer needed to save money on edits. What is
left unsolved is precisely job A, the base frame, which is **one call per chain** and the one
place the register is decided. That is a smaller, better-defined target than the workstream
started with, and it is exactly what a style LoRA is for.

### 8.5 Revised order of work

1. **Adopt banana base plus lite edits** as the production default, pending Luca's eye on a
   full 300-frame loop. Rename it rather than folding it into banana interpolation v1.
2. **Put the register clause in `BASE_SUFFIX`** (section 1.2). Now more urgent, not less: the
   base frame is the single remaining register risk and it has no other guard.
3. **P2, the klein style LoRA**, targeting job A only. The edit LoRA drops in priority because
   lite already edits well; keep the 113 pairs, but the style LoRA is now the artefact that pays.

State 9 asks for the opening state back: completely clear air, everything crisp.

- **Banana state 9** holds the register. Soft tonal, muted grey-green, blended. It has drifted

**The two models fail differently and the difference decides it.** A geometry walk is a bad

### 9.3 The confound was real, and partial

The receding-mist arc restores detail, so it invites crispening from any model, and the control
proves it: **banana also ends above 1.0, at 1.28.** Without the control this would have been
reported as a lite defect when roughly half of it is the arc. Lite is worse by about 60% on
surface and by 3.3x on final-pair chroma, and that margin is the finding.

Running the control cost $0.60, two thirds of the test's total, and it changed the conclusion
from "lite breaks" to "lite breaks about 60% harder than the incumbent on an arc that breaks
both". **Budget the control. A one-sided chain measurement cannot conclude.**

### 9.4 Where the boundary actually sits

Lite's untouched-region lapvar by pair: 1.00, 0.97, 0.97, 0.71, 1.16, 1.15, **1.42**, 1.09,
**1.77**. Clean through pair six, then it goes.

**This lands exactly on doctrine that already exists.** The edit-model-loop skill says: *"Keep
any SEQUENTIAL run to about five edits. At nine, geometry walks."* T1 deliberately violated that
cap as a stress test. The finding is therefore not "lite is unusable" but:

> **Flash-lite is safe inside the five-edit sequential cap the doctrine already imposes, and it
> is LESS tolerant of exceeding that cap than nano banana is.**

Production chains are authored as short sequential runs joined by bridges, so the saving in
section 8 survives. What does not survive is the unqualified phrase "hand the nine edits to lite".

## 10. T2, the five-edit ceiling and the bridge (2026-08-18)

**Two answers: the ceiling is real and lite is BETTER than banana beneath it; the bridge is
where lite fails.** Cost $0.10, all of it on the two bridge calls. The five-edit half was free,
because T1's first five lite edits share an anchor and instructions with what a fresh run would
have produced. Session total $1.30.

### 10.1 The ceiling, measured rather than assumed

Section 9 put the boundary at "about five" on doctrine. Measured in the untouched foreground,
against frame 0, where the mist cannot confound it:

| state, vs frame 0, untouched region | banana ssim / lapvar | lite ssim / lapvar |
|---|---|---|
| **state 5** | 0.707 / 0.67 | **0.748 / 0.77** |
| state 9 | 0.663 / 1.29 | **0.532 / 2.46** |

**At five edits lite beats the incumbent. By nine it is at 2.46x surface against banana's
1.29x.** The crossover is real, it sits between five and nine, and the exact pair where lite
turns is 6->7 (lapvar 1.42, section 9.1). So **six is the last safe pair and five is a correct
working cap** with one pair of margin.

### 10.2 The bridge: lite collapses onto the nearer endpoint

The dual-image call, `--bridge 0000 0004 --bridge-at halfway`, on the banana-authored endpoints
of `action_mist`. PL17's bar: a true in-between is closer to each endpoint than the endpoints
are to each other.

| candidate | ssim to 0000 (clear) | ssim to 0004 (mist) | verdict |
|---|---|---|---|
| endpoints to each other | 0.733 | - | the bar |
| naive pixel lerp | 0.932 | 0.859 | between, but ghosts |
| **banana bridge** | **0.798** | **0.923** | genuine intermediate |
| **lite bridge** | **0.736** | **0.980** | **near-copy of the endpoint** |

**0.980 to one side is the stop signal the plan of record already names**: "STOP bridging if a
bridge comes back as a near-copy of an endpoint". Lite clears the bar on the far side by 0.003,
which is arithmetic, not an in-between.

Confirmed by eye, and this is the clearer instrument. The requested moment is halfway between
clear air and 75% depth veiling, so roughly 37%: ridge softened, farmhouse soft, poplars still
crisp.

- **Banana's bridge lands there.** Ridge pale but present, farmhouse visible and soft, poplars
  readable. A real intermediate at roughly 45%.
- **Lite's bridge lands at roughly 75%**, which is the endpoint it was handed.

**Lite's bridge failure is POSITIONAL, not stylistic.** The register in its bridge is clean:
soft tonal, no mottling, no hard outlining. It paints our picture correctly and puts it at the
wrong moment. That is a different failure from section 9's, and it is the one that matters for
chain assembly, because bridges are what join short runs.
